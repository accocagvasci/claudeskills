# Webots Web Deployment Reference

This reference documents deployment-facing interfaces for Webots web delivery workflows.

## 1) W3D format specification overview

### Purpose

W3D is a web-oriented scene export format generated by Webots for browser rendering.

### Core characteristics

- Serialization style: XML-based scene description.
- Usage model: static scene visualization (non-interactive simulation execution).
- Generation path: `File > Export W3D` in Webots.
- Consumption path: rendered in browser through a compatible WebGL pipeline, commonly via `webots-view`.

### Typical content classes

- Scene graph hierarchy and node transforms.
- Geometric meshes and primitive shapes.
- Material/appearance assignments supported by the exporter.
- Texture references and static visual attributes.

### Known unsupported nodes and limits

- `Skin` nodes are not supported in W3D export output.
- `Pen` nodes are not supported in W3D export output.
- Runtime controller logic is not represented in W3D static output.
- Dynamic simulation state changes are not replayed unless using animation export.

## 2) `webots-view` web component API

`webots-view` is the browser-side component used to display exported scenes, animations, or streams.

### Integration role

- Load and display Webots-compatible web content in an HTML page.
- Connect to stream sources over WebSocket for live visualization.
- Provide a reusable element for embedding in documentation sites, demos, and portals.

### Generic embed shape

```html
<webots-view
  id="viewer"
  style="width: 100%; height: 600px;"
></webots-view>
```

### Common integration patterns

- **Static scene loading:** bind element to exported W3D resource location.
- **Animation playback:** point element/page logic to HTML5 animation artifact.
- **Live stream rendering:** provide stream endpoint from Webots `--stream` server.

### Practical implementation notes

- Keep container dimensions explicit to avoid zero-height rendering issues.
- Initialize only after DOM readiness in dynamic single-page applications.
- Use secure WebSocket (`wss://`) when serving over HTTPS.

## 3) WebSocket protocol messages

Web streaming uses WebSocket-based communication between browser clients and Webots backend services.

### Transport model

- Protocol: WebSocket.
- Topology: one simulation source, multiple viewers supported.
- Direction: bidirectional channels may carry scene/state updates and optional control/session messages.

### Message category overview

Exact payload schema can vary by runtime version; integration should handle categories rather than hard-coded assumptions.

- **Session/control messages:** session setup, identification, readiness, and teardown.
- **Scene metadata messages:** world metadata, node descriptors, static resource mapping.
- **State/frame update messages:** transform changes, sensor/visual updates, frame progression.
- **Event messages:** status notifications, warnings, stream lifecycle updates.

### Robust client handling guidance

- Validate message type/category before applying payload.
- Tolerate unknown message fields for forward compatibility.
- Apply frame updates in order when sequence metadata is available.
- Implement reconnect logic with exponential backoff for transient failures.

## 4) `webots.yaml` configuration reference

`webots.yaml` defines publication metadata and deployment mode for webots.cloud-oriented workflows.

### Canonical publish section

```yaml
publish:
  type: demo
  title: "My Simulation"
  description: "A demo of my robot"
```

### Key fields

- `publish.type`
  - Purpose: publication mode selector.
  - Typical values: `demo`, `competition`, `animation`.
- `publish.title`
  - Purpose: human-readable entry title shown in hosted catalogs/pages.
- `publish.description`
  - Purpose: short project summary for browser consumers.

### Configuration practices

- Keep `publish` metadata aligned with actual repository artifacts.
- Use `animation` mode when publishing pre-recorded playback content.
- Use `demo`/interactive modes with Dockerized runtime when live interaction is required.

## 5) Docker image tags and variants

Interactive cloud deployments commonly derive from the official webots.cloud image family.

### Base image example

```dockerfile
FROM cyberbotics/webots.cloud:R2025a-ubuntu22.04
COPY . /usr/local/webots-project/
```

### Tag strategy

- Use release-pinned tags (for example `R2025a-ubuntu22.04`) for repeatable builds.
- Avoid floating `latest`-style tags in production deployment pipelines.
- Match Ubuntu/runtime variant with project dependency constraints.

### Variant considerations

- Webots release level (`R20xx*`) affects runtime and compatibility.
- OS base suffix (for example `ubuntu22.04`) affects package availability and ABI behavior.

## 6) Session/Simulation server configuration options

Interactive web deployment architecture separates orchestration and execution concerns.

### Session Server

- Manages user sessions and simulation allocation.
- Tracks lifecycle: create, active, timeout, terminate.
- Routes clients to available simulation instances.

### Simulation Server

- Runs individual Webots simulation processes.
- Publishes WebSocket stream endpoints for attached clients.
- Enforces per-instance resource boundaries (CPU, memory, lifetime).

### Operational configuration dimensions

- Instance limits and concurrency ceilings.
- Idle timeout and maximum session duration.
- Port allocation strategy and endpoint advertisement.
- Health checks and restart policies.
- Logging level for diagnostics and usage auditing.

## 7) Command-line streaming options

### Core commands

```bash
webots --stream
webots --stream="port=1234"
webots --batch --stream my_world.wbt
```

### Behavior summary

- `webots --stream`
  - Launch Webots with default streaming settings.
- `webots --stream="port=1234"`
  - Launch streaming server on explicit port.
- `webots --batch --stream my_world.wbt`
  - Run headless/batch mode while exposing live stream for remote clients.

### Deployment notes

- Expose configured stream port through firewall or container networking.
- Prefer explicit port assignment in orchestrated environments.
- Combine with process supervision for long-lived stream services.

## 8) Browser compatibility matrix

| Browser family | Support expectation | Notes |
|---|---|---|
| Chromium-based (Chrome, Edge, Brave) | Strong | Preferred baseline for validation and demos |
| Firefox (Gecko) | Good | Validate WebGL and WebSocket behavior per release |
| Safari (WebKit) | Partial to Good | Verify WebGL features, performance, and media autoplay policy |
| Mobile browsers | Variable | Validate touch interaction, memory pressure, and GPU limits |

### Compatibility validation checklist

- Confirm WebGL context creation and scene rendering.
- Confirm WebSocket connectivity and sustained updates.
- Confirm animation playback timing and control responsiveness.
- Confirm layout sizing for embedded `webots-view` containers.

## 9) Known web limitations

### Export and rendering limits

- `Skin` nodes unsupported in W3D export.
- `Pen` nodes unsupported in W3D export.
- Static W3D scenes do not execute simulation logic.

### Streaming/deployment limits

- Stream quality depends on network latency and bandwidth.
- Browser resource constraints can limit very large scenes or high update rates.
- Feature parity across browsers is not guaranteed for advanced WebGL behavior.

### Mitigation guidance

- Replace unsupported nodes with browser-compatible alternatives before export.
- Reduce scene complexity for constrained devices and mobile clients.
- Run cross-browser smoke tests before publication.
